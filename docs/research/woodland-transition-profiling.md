# Generated woodland boundary profiling (2026-09-23)

The generated-world Shipping route teleports only to its surveyed walk start, then holds mapped movement across the old -4000 edge and the -4800 chunk seam. It excludes screenshot readback/startup from the reported cadence. These are offscreen game-thread wall times, not GPU, Present or physical display measurements. The older woodland-polish reference was 690.414 ms; a subsequent selected-build run measured 789.200 ms. Load differs between runs, so comparisons below use the same route and instrumented code before/after the one sampling change.

At the pre-change boundary, five cover chunks spent **328.983 ms** placing instances; outer/active tree desired-list preparation took **244.271/153.759 ms**. Deferring cover HISM registration did not improve either measurement and was reverted. The dominant cost was repeated analytic `SampleTerrain` calls inside `GroundHeight` (four samples per point, nine points per mature tree). The retained change interpolates the same four canonical `ChunkBaseline::terrain` heights when that already-prepared tile is cached and otherwise calls the original height function. The Shipping route verifies cached and canonical heights across the negative chunk seam, including edges. Generated keys, terrain geometry, collision, felling, construction, regional water and current-version save/reload still pass the ordinary route; `stream-profile-04-consumer` also reloaded the producer save in a separate process without changing its bytes.

The first cached-height trial still left a **64–67 ms** world refresh; subphase measurement later revealed another **71.504 ms** of simulation region activation on the same crossing. `Materialize` had synchronously regenerated nine immutable chunk baselines. It now consumes world-owned baselines only when descriptor and chunk identity match, otherwise using the original generator. A portable parity/mismatch test rejects a wrong key or world seed without mutating the simulation; the Shipping route preserves serialization and stable IDs. The active-tree rebuild retains existing capsules only for identical key, transform, dimensions and resource handle. With overlap, capsule teardown/registration decreased while felling still removes the correct capsule.

The remaining ordinary-walk work was five incoming cover batches and new resource visuals. During movement toward one adjacent destination, the world stages those render-only components over successive game ticks, with a **4 ms intended budget per tick**; a single atomic batch can exceed that soft budget, and the highest measured staging call was **4.163 ms at 720p / 6.025 ms at 4K** in the final build. They are registered hidden with collision disabled until an exact world/chunk/revision/signature match commits them. Changing destination cancels and destroys them; controlled supersession checks now build both future cover and resource sets for opposite directions before checking no hidden blocker or authoritative-state mutation. Missing or mismatched staging never impersonates a valid resource and falls back to the existing synchronous build only for a valid, current destination. Five staged cover chunks and 78 staged resource visual groups were adopted on the measured crossing.

**Actual player-frame observation:** `stream-profile-09` measured a 44.819 ms worst mapped-walk tick (one frame over 33.3 ms); the final `stream-profile-14` measured **27.819 ms** and its 4K companion **27.749 ms**, both with **zero frames over 33.3 ms** on the tested walk. World-only refresh is not the whole frame; the new route enforces the longest-frame and staging thresholds, not just p95. The final candidate also passed a separate-process producer/consumer save, ordinary felling/building/collision/regional-water route and normal non-QA startup in an isolated profile. Captures at the untouched and boundary cameras differ only modestly from the pre-staging candidate (mean RGB delta 0.93/2.94 at 720p in the earlier identical-production `-11` trial), not a subjective art endorsement. GPU/Present/VRR timing and physical controller comfort remain unmeasured.

Old-terrain teardown was **0.27–0.34 ms** and existing terrain collision toggling **0.10–0.15 ms**. New terrain sections took roughly **0.5–0.6 ms each including collision cooking**. The installed engine combines mesh publication and physics cooking inside `CreateMeshSection_LinearColor`, so the separate internal cook cost remains unmeasured. Uncached teleports, cold starts and unusual machine load can still exceed the tested boundary budget; they are not represented as hitch-free.
